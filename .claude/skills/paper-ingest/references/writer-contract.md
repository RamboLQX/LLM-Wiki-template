# Writer Agent 契约

根据主提示提供的结构化提取稿撰写指定章节。不要读取论文原文，不要写入 wiki。前三节 Writer 只写第 1–3 节；后三节 Writer 只写第 4–6 节及存在性 JSON。

## 通用格式

每节严格使用：

```markdown
## {编号}. {标题}

**本节结论**：一句话直接给出本节最核心的结论。

围绕证据和解释展开正文。仅在信息天然适合枚举或比较时使用列表、公式或表格，不重复本节结论。
```

六节正文通常合计 2500–4500 个中文字符。各节字数为软范围：信息简单时可以更短，核心方法或证据复杂时可以超过建议上限。不得为了压缩而省略关键机制、证据或结论边界，也不得为达到篇幅填充重复内容。

## 证据规则

- 论文明确报告的内容可直接陈述，但必须忠于提取稿。
- 作者解释使用“作者认为”或“作者解释”标识。
- 分析者推断使用“据此可推断”或“从方法上看”标识。
- 提取稿标记“论文未报告”或“不适用”的内容不得补造。
- 不为满足固定结构强行生成实验、消融、公式、数据集或贡献。
- 与既有研究的比较只使用主提示提供的 KB 上下文，不凭记忆虚构 wiki 来源。
- 每个重要判断都要说明依据及其适用范围，避免只给结论而不展开推理链条。

## 第 1–3 节

### 1. 研究问题与动机

- 本节结论直接回答论文要解决什么问题、为什么重要。
- 正文说明领域背景、已有方法或观点为何不足、研究缺口如何形成，以及论文的核心主张如何回应这一缺口。
- 建议 350–600 个中文字符。

### 2. 核心方法

- 本节结论直接回答论文使用什么方法或论证框架、核心创新是什么。
- 正文展开整体处理链条或论证框架，说明关键模块的输入输出、内部机制、交互关系、设计动机和成立假设。
- 解释创新点解决了什么具体问题，以及它与常规方案的实质差异。
- 仅在论文确有公式和参数时使用 LaTeX 与具体数值。
- 建议 600–1000 个中文字符。

### 3. 实验设计与结果

- 本节结论直接回答论文使用什么证据支持了什么发现。
- 实证研究分析数据集、任务设置、基线、指标、关键数字、消融和稳健性，明确每组关键证据验证了哪个主张。
- 理论、综述或观点论文按实际证据类型分析，不强行套用实验结构。
- 区分结果实际支持的结论与作者进一步推断的内容，对证据可信度、外推范围和异常结果做出有依据的判断。
- 建议 600–1000 个中文字符。

第 1–3 节必须使用以下精确标题：

```text
## 1. 研究问题与动机
## 2. 核心方法
## 3. 实验设计与结果
```

## 第 4–6 节

### 4. 与相关工作的比较

- 本节结论说明与已有工作的根本区别。
- 正文结合 KB 上下文和论文自身讨论，从问题设定、方法机制、证据基础、性能收益和适用边界中选择有效维度进行实质性比较。
- 不并列复述多篇摘要；解释差异为何产生、是否构成真实改进以及代价是什么。
- KB 为空时只分析论文自身讨论的相关工作。
- 建议 400–700 个中文字符。

### 5. 局限性与未来工作

- 本节结论说明最关键的局限性。
- 区分作者承认的局限、分析者识别的问题和未来方向，并说明这些局限会影响哪些结论、场景或外推范围。
- 建议 250–450 个中文字符。

### 6. 我的评价与启发

- 本节结论说明最值得记住的贡献或启发。
- 给出 X/10 评分及理由，综合贡献新颖性、证据充分性、可复现性和适用范围形成独立判断。
- 分析哪些设计可以迁移、迁移需要满足什么条件，以及能够形成哪些具体后续研究问题。
- 评分参考：1–3 明显缺陷；4–6 增量贡献；7–8 显著推进；9–10 里程碑工作。
- 建议 300–500 个中文字符。

第 4–6 节必须使用以下精确标题：

```text
## 4. 与相关工作的比较
## 5. 局限性与未来工作
## 6. 我的评价与启发
```

## 存在性检查

后三节 Writer 只检查结构化提取稿实体与概念清单中的实际数据行。清单可以为空，不把表头、说明文字或“无”当作条目。

对每个实体在 `wiki/entities/` 中按名称搜索；对每个概念在 `wiki/concepts/` 中按名称搜索。三节正文后输出：

```text
---EXISTENCE---
{"entities":[{"name":"名称","exists":true,"file":"wiki/entities/页面.md"}],"concepts":[]}
```

没有条目时输出 `{"entities":[],"concepts":[]}`。只输出指定章节与存在性 JSON，不添加执行说明。
